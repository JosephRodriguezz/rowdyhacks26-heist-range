## Executive Summary

This specification establishes the architectural and algorithmic foundation for the Blue Team defense capabilities within the RANGE cybersecurity competition framework. It formalizes:
1. **Deterministic Telemetry Clustering:** Correlating atomic telemetry events into bounded multi-session threat clusters using temporal windows ($W = 60\text{s}$) and maximum cluster lifetimes ($L_{\max} = 300\text{s}$) across shared entities.
2. **Explainable Additive Risk Scoring:** A transparent, bounded scoring model ($0 \le \text{Risk} \le 100$) evaluating threat impact, resource exposure, cluster breadth, and post-containment persistence, categorized into four discrete operational severity bands based on score component contributions.
3. **Confidence-Driven PACE Response Matrix:** A tiered response framework adapted as an operational planning analogy where certainty dictates action: high-confidence, policy-verified violations trigger immediate single-session containment (Primary), anonymous reads route to source remediation proposals (Alternate), and uncertain exploratory probes trigger evidence gathering without disruptive action.
4. **MITRE D3FEND Armor Model:** A 7-tactic defensive hierarchy mapped 1:1 to bank heist presentation themes, applying state-based score credit (0% proposed, 15% contained, 50% applied patch, 100% referee-verified, cracked on failure) and aggregated via path-minimum headline scoring across remediable attack paths.
5. **Modular Role Architecture:** Eight discrete functional specialists implemented and unit-tested once, composed into a two-character pairing (**Monitor** and **Defender**) for initial demonstration, and dynamically unbundled into an eight-agent swarm mode post-demo following initial demo success.

All algorithmic weights, window durations, cluster thresholds, and thematic designations within this document are designated **proposed project defaults** and adaptations, not standards-derived constants.

**Contract Reality & Capability Classification:**
To adhere strictly to repository rules forbidding claims of live capability from design text, all capabilities in this specification are classified into three distinct operational groups based on the actual modules present in `backend/app/agents/blue/` (`detection.py`, `frameworks.py`, `incident.py`, `observe.py`, `patches.py`, `proposals.py`, and `report.py`):
- **Group A (Implemented in code today):** Policy-scoped detection of `cross_user_read` and `anonymous_read` (`detection.py`); generation of one `revoke_session` proposal per offending session with no cap, queue, depth reporting, or operator alert (`proposals.py`); the `ownership-fix-001` patch proposal as a draft (`proposals.py`, `patches.py`); incident evidence reporting (`incident.py`); and `observe()` with its strict context enforcement (`observe.py`).
- **Group B (Specified and implementable on today's telemetry contract, but not built):** Telemetry cluster grouping and sizing (no clustering or sizing code exists yet in `backend/app/agents/blue/`; closing tasks: B-07 / B-10), explainable additive risk scoring (closing tasks: B-07 / B-10), full PACE planner tier escalation logic, posture accounting, and the 5-per-60s circuit breaker rate cap and containment queue (which remains OFF by default until core replays pending evidence and provides event timestamps under B-12).
- **Group C (Specified, but inert until B-12 supplies event IDs on telemetry):** Persistence credit ($\text{Persistence} = 25$), Alternate source remediation on containment bypass, armor cracking, and all other ordering-dependent state transitions.
The first demonstration must not claim or show Group B or Group C capabilities.

## 1. Architectural Foundation & Core Boundaries

### 1.1 Core Execution Boundary (Decision 0004)
The blue defense subsystem operates strictly as an **advisory intelligence and proposal engine**. Under Decision 0004:
- **AI Specialists Propose:** Blue agents and algorithmic components inspect sanitized telemetry and policy, generating structured proposals (`range.blue.observe/v1`).
- **Core Dispatcher Executes:** Only the deterministic core control plane executes approved actions against the target lab environment.
- **Referee Verifies Independently:** Only the independent referee (`verify(candidate, tools)`) determines whether a security vulnerability is mitigated. Blue components never verify their own fixes and never mark incident reports or armor postures as "resolved" or "verified" based on self-assessment.
- **Containment $\ne$ Fix:** Session revocation stops an active threat stream but leaves the root software vulnerability intact. Containment is always labeled `effect: "containment"` and never reported as a permanent remediation.

### 1.2 Registered Lab Targets & Action Allowlist
To prevent tool misuse, SSRF, and unintended blast radius:
- Actions operate exclusively against registered lab targets resolved through a static target registry (`storefront-lab`).
- Target URLs must be origin-bound. Relative paths beginning with `//`, host modifications, proxy injection, and external redirects are rejected at the core boundary.
- Blue proposals are restricted to contract-approved action types:
  - `revoke_session`: Invalidates a specific, implicated session reference.
  - `apply_patch`: Directs core to apply a pre-packaged, version-pinned source patch from `defenses/patches/` to a disposable target instance.

### 1.3 Strict Context Allowlist & Memory Isolation
In accordance with `backend/app/agents/blue/observe.py`:
- Contexts must contain only: `target_id`, `target_version`, `data_source`, `telemetry`, `access_policy`, `previous_defenses`, `budgets`, `assessment_id`, and `generated_at`.
- Any presence of `events`, `candidates`, `findings`, `ground_truth`, `red_*`, or `verdicts` raises an immediate `ContextError`, failing closed to guarantee absolute red/blue isolation.

## 2. Telemetry Scoping & Threat Isolation

### 2.1 Sanitized Telemetry Schema
In the current live contract (`shared/contracts/README.md` line 41), telemetry records contain: `request_id`, `timestamp`, `target_id`, `target_version`, `actor_ref`, `session_ref`, `resource_id`, `resource_owner_ref`, `action`, and `http_status`. The `event_id` field on telemetry records is a **proposed field for B-12** (Member 2). The sample schema below illustrates the proposed target schema rather than the current contract shape, and this specification makes no claim of a live capability under M1:
```json
{
  "event_id": 42,
  "request_id": "req-0042",
  "timestamp": "2026-10-02T20:14:05.120Z",
  "target_id": "storefront-lab",
  "target_version": "lab-v1",
  "actor_ref": "actor-attacker-1",
  "session_ref": "sess-alpha-88",
  "resource_id": "order-204",
  "resource_owner_ref": "bob",
  "action": "read_private_order",
  "http_status": 200
}
```

> [!NOTE]
> Per the shared contract, `actor_ref` represents an authenticated identity reference (e.g. `actor-attacker-1`, `alice`). For unauthenticated or anonymous access, `actor_ref` is strictly `null` (never a synthetic string such as `'actor-anon-9'`).
> While `shared/contracts/README.md` defines `event.id` on the unified event stream, `event_id` directly on telemetry records is a proposed B-12 contract extension field. In this proposed target architecture, `event_id` serves as the authoritative integer sequence identifier or monotonic cursor assigned by core (`telemetry_seq` or unified event stream sequence). While `timestamp` provides human-readable display context, `event_id` is authoritative for all event ordering, state transitions, persistence credit, and armor cracking. In the current contract shape where telemetry records lack `event_id`, ordering-dependent state transitions default to inconclusive.


### 2.2 Scoping, Filtering, and Secret Redaction
1. **Target and Version Scoping:** Records with mismatched `target_id`, `target_version`, or `assessment_id` are routed to `skipped` with a documented reason and never alerted upon.
2. **Deterministic Deduplication:** Records are validated via `detection.record_problem` before their `request_id` is registered in seen sets, preventing malformed telemetry from suppressing valid alerts.
3. **Secret Redaction & Canonical Digests:** Any telemetry field containing sensitive keys (`password`, `token`, `cookie`, `authorization`, `api_key`, `secret`) is stripped prior to detection, evidence compilation, or digest computation. All SHA-256 evidence digests and report signatures are computed strictly over the **redacted canonical JSON representation** (keys sorted, whitespace normalized, secrets omitted). Evidence hashing, incident report evidence verification, and the deduplication `request_id` check use this identical normalization so that integrity digests are deterministically reproducible without leaking secrets.
4. **Untrusted Target Content:** Response bodies and user-supplied parameters are treated as untrusted data. Model reasoning never uses unparsed target payloads to authorize actions.

## 3. Telemetry Cluster Grouping Rules & Taxonomy

### 3.1 Deterministic Ingestion & Chronological Ordering
To ensure determinism and reproducibility across varying network delivery orders or batch partitions:
1. **Authoritative Event-ID Ordering for State & Ordering Decisions:** Per `shared/contracts/README.md`, event IDs provide authoritative order on the event stream (`event.id`), while timestamps are display data. Supplying an authoritative `event_id` directly on telemetry records is a field proposed for B-12; the spec makes no claim of a live capability under the current contract shape. In this target architecture, telemetry records passing scope and schema validation are ordered primarily by the authoritative event ID or sequence cursor supplied by core (`telemetry_seq` or unified event stream sequence). Event IDs are authoritative for state ordering decisions: cluster sequence, persistence credit evaluation, and armor cracking transitions. Remediation dwell duration, rolling windows, and lifetime caps are time-based and measured using core-stamped monotonic effective timestamps ($t_{\text{eff}}$), not event IDs.
   - **Contract Dependency:** Core must supply an authoritative event ID on all telemetry records. The blue design formally establishes this proposed B-12 contract dependency and assumes core provides it in future milestones.
   - **Missing Ordering Reference Rule:** In the current contract shape where telemetry records lack `event_id`, or if an authoritative ordering reference is missing on a record that an ordering decision depends on (e.g. determining whether an unauthorized read occurred before or after a defense execution), the outcome is strictly **inconclusive**: no persistence credit is awarded ($\text{Persistence} = 0$), no armor status transition occurs, and an explanatory limitation note naming the missing reference (`"inconclusive_ordering_missing_event_id"`) is recorded.
2. **Display Timestamp Fallback & Deterministic Tie-Breaking:** When evaluating environments where only raw telemetry timestamps are supplied, records are sorted chronologically by `timestamp` in ascending order. If two records share the exact same timestamp string, sorting breaks ties deterministically using `request_id` in ascending alphanumeric order. However, display timestamps never override or substitute for event-ID ordering in state transitions (persistence and armor cracking).
3. **Invariance Guarantee:** Shuffled or out-of-order batches of identical telemetry records produce the exact same sorted stream and consequently identical cluster groupings.
4. **Governing Core-Stamped Timestamps for Windows and Dwell Duration:** The 60-second inactivity window, the 300-second lifetime cap, and the 30-second remediation dwell use core-stamped timestamps, meaning timestamps set by core or the lab and never by a client, and only to measure elapsed time. Membership and state ordering use event ID order. Records are deduplicated by `request_id` before any window is applied, so a replayed record adds no membership.
5. **Monotonic Clamping & Time Anomaly Handling:** Elapsed time is computed from a monotonic clamp of the core timestamps taken in event-ID order, so clock skew cannot stretch or shrink a window. For an event-ordered stream $R_1, R_2, \dots$:
   $$t_{\text{eff}}(R_k) = \max\Big(t(R_k), t_{\text{eff}}(R_{k-1})\Big)$$
   A record whose timestamp goes backwards in event-ID order ($t(R_k) < t_{\text{eff}}(R_{k-1})$) is clamped to $t_{\text{eff}}(R_{k-1})$ and gets a `"time_anomaly"` note in cluster `notes`. Effective time within an active cluster is strictly non-decreasing ($t_{\text{eff}} - T_{\text{last}}(C) \ge 0$), preventing clock skew from prematurely closing clusters or evicting events.

### 3.2 Spatial & Temporal Correlation Window ($W = 60\text{s}$, $L_{\max} = 300\text{s}$)
Adversary activities often distribute across multiple HTTP requests, rapid recon bursts, or distinct sessions. The **Swarm Correlator** links atomic telemetry events into cohesive clusters using graph connectivity within a rolling temporal window:
- **Partition Key & Record Eligibility:** Before graph construction, telemetry records are strictly partitioned by a composite key:
  $$\text{PartitionKey} = (\text{assessment\_id}, \text{target\_id}, \text{target\_version}, \text{data\_source}, \text{policy\_id}, \text{attack\_type})$$
  Only eligible records (valid, secret-redacted records passing target/version scope checks and classified by detection policy) sharing the exact same partition key can form edges. Records evaluating different policies or classified with different attack types (e.g. `cross_user_read` vs. `denied_probing`) are partitioned into separate clustering graphs, ensuring unambiguous impact classification within every cluster. Probing and successful unauthorized reads never share a cluster.
- **Rolling Inactivity Window Duration ($W$):** 60 seconds. Evaluated using core gateway monotonic effective time ($t_{\text{eff}}$). A record $R$ with effective timestamp $t_{\text{eff}}$ can attach to an active cluster $C$ within the same partition only if $t_{\text{eff}} - T_{\text{last}}(C) \le 60\text{s}$. If $t_{\text{eff}} - T_{\text{last}}(C) > 60\text{s}$, cluster $C$ is closed due to inactivity.
- **Maximum Cluster Lifetime Cap ($L_{\max}$):** 300 seconds (5 minutes). Evaluated using core gateway monotonic effective time ($t_{\text{eff}}$). A cluster closes permanently when $t_{\text{eff}} - T_{\text{first}}(C) > 300\text{s}$. Any subsequent related events arriving after 300 seconds from the cluster's first event seed a new distinct cluster. This cap prevents indefinite chaining of ongoing operational traffic.
- **Exact Boundary Semantics:** Boundaries are inclusive of equality ($\le 60\text{s}$ and $\le 300\text{s}$) and strictly partitioned when exceeded ($> 60\text{s}$ or $> 300\text{s}$).

### 3.3 Linkage Heuristics & Deterministic Graph Construction
Within an active partition, edges are constructed according to deterministic precedence:

```
                          LINKAGE HEURISTICS (Within Same PartitionKey)
                          
  [ Strong Link ]         shared session_ref (R_i.session == R_j.session != null) -> Always joins
         OR               shared actor_ref   (R_i.actor == R_j.actor != null)     -> Joins across sessions
                          ------------------------------------------------------------------------
  [ Weak Link ]           resource overlap   (R_i.resource == R_j.resource != null)
         OR               sequential IDs     (|numeric_id(R_i) - numeric_id(R_j)| == 1)
                          (Weak links NEVER merge clusters; populate 'related_clusters' list ONLY)
                          ------------------------------------------------------------------------
  [ Null Actor / Distinct Sessions Guard ]
                          R_i.session != R_j.session AND (R_i.actor == null OR R_j.actor == null)
                          -> never merge; partition into separate clusters (TEST-BND-18)
```

1. **Strong Links (Merge Records into One Cluster):**
   - **Shared Session Reference ($R_i.\text{session\_ref} == R_j.\text{session\_ref} \neq \text{null}$):** A shared non-null session reference is the strongest link and **always joins records into one cluster** within window $W$.
     - *Identity Conflict Resolution:* If records sharing a session carry different non-null `actor_refs`, this represents an identity conflict (e.g., session hijacking, token cycling, or telemetry anomaly). They **stay in one cluster** (session continuity governs), both actors are recorded in cluster metadata (`actors: ["actor-1", "actor-2"]`), and an explanatory note `"identity_conflict"` is recorded in cluster `notes`. An identity conflict does not alter cluster sizing ($N_{\text{sessions}} = 1$) or risk scoring.
     - *Asymmetric Null Actor:* If records share a session where one record has `actor_ref: null` and the other has a non-null `actor_ref`, they join on the strong session edge into a single cluster attributed to the non-null actor.
   - **Shared Actor Reference ($R_i.\text{actor\_ref} == R_j.\text{actor\_ref} \neq \text{null}$):** Non-null authenticated actor equality joins records into the same cluster across distinct sessions of that actor within window $W$ (e.g. an attacker rotating sessions under a single identity).
   - **Null Identity Guard:** Null or empty identities (`null`, `""`) never link to each other on the basis of null equality.
2. **Weak Links (Relationships Across Clusters — Never Merge Clusters):**
   - Weak links never create merge edges; they only populate a cluster's `related_clusters` list.
   - **Definition of Related:** Two clusters are related when records in them touch the same resource, or sequential resources, from different non-null `session_refs`; an `actor_ref` may be null, and a null `session_ref` never relates anything.
   - **Invariance Rule:** Weak links **never merge clusters and never change a cluster's size ($N_{\text{sessions}}$) or risk score**.
   - **Separate Related List:** Instead of merging graphs, weak links populate each cluster's separate `related_clusters` metadata list (e.g., `related_clusters: [{"cluster_id": "cluster-xyz", "relation": "resource_overlap", "resource_id": "order-204"}]`). Any rule applying weak links within records already sharing an `actor_ref` is eliminated, as shared `actor_ref` is already a strong link.
3. **Anonymous Records Linkage:**
   - Anonymous clusters key strictly on the resource: records where `actor_ref: null` and `session_ref: null` accessing the **exact same private `resource_id`** within window $W$ link together into an anonymous cluster ($N_{\text{sessions}} = 0$, size `unknown`).
   - **Distinct Resources Accessed Anonymously:** Distinct private resources accessed anonymously (e.g., anonymous request to `order-204` and anonymous request to `order-205`) **never link together**; they form **distinct independent clusters**, each of size `unknown`, each with $N_{\text{unauth\_resources}} = 1$ and scored independently.
4. **Resource Overlap Across Distinct Sessions with Null Actor (Never Merge):**
   - A record with a null `actor_ref` and a non-null `session_ref` never merges with records with different sessions (even when accessing the same resource); they never merge and are partitioned into separate clusters.
   - Specifically, if two records access the same `resource_id` across distinct session references ($R_i.\text{session\_ref} \neq R_j.\text{session\_ref}$) where one or both records have `actor_ref: null` (for instance, an unauthenticated request with a session token but no user identity, or an anonymous session alongside an authenticated session), they **never merge clusters**.
   - **Rationale:** Null actor values cannot establish common identity, and distinct sessions preclude strong session linkage. The records are deterministically partitioned into separate clusters. Any resource overlap populates `related_clusters` under the single rule defined in §3.3.2 (two clusters are related when records in them touch the same resource from different non-null `session_refs`; an `actor_ref` may be null, and a null `session_ref` never relates anything). This ensures that resource overlap with missing identity never creates spurious multi-session clusters (governing TEST-BND-18).
5. **Deterministic Cluster Identifiers:** Derived deterministically from cluster metadata and sorted member records:
   $$\text{cluster\_id} = \text{"cluster-" } + \text{target\_id} + \text{"-" } + \text{version} + \text{"-" } + \min(t) + \text{"-" } + \text{SHA256}(\text{sorted\_request\_ids})[:8]$$

### 3.4 Deterministic Transitive Bridging Guard
To ensure deterministic graph construction and prevent over-attribution across distinct actors:
1. **Weak Links Never Bridge Distinct Actors:** If two records have different non-null actor references ($R_i.\text{actor\_ref} \neq R_j.\text{actor\_ref}$), weak links never create graph edges and never merge clusters. Distinct identified actors **always form separate clusters**.
2. **Deterministic Partitioning:** A fixture of 5 distinct authenticated actors accessing the same private resource concurrently deterministically produces **five separate `solo` clusters**, each with $N_{\text{sessions}} = 1$, each scored independently, with the other clusters recorded in `related_clusters`. It never produces a merged `crew` or `syndicate`.
3. **Prohibition Applies Only to Weak Links:** The prohibition on joining different actors applies strictly to weak links. A shared non-null session reference always joins records into one cluster per §3.3.1, with any differing actor references flagged as `identity_conflict`.
4. **Sequential Traversal Limit:** Sequential ID traversal across distinct actors represents independent exploratory activity and is never merged.

### 3.5 Cluster Sizing Taxonomy & Session Cardinality
Per Decision 0006, cluster size is determined **strictly by observed non-null session cardinality inside one cluster** ($N_{\text{sessions}}$):
- **Solo Operative (`solo`):** Exactly 1 distinct non-null `session_ref` ($N_{\text{sessions}} = 1$).
- **Strike Crew (`crew`):** 2 to 4 distinct non-null `session_refs` ($N_{\text{sessions}} \in [2, 4]$).
- **Syndicate Swarm (`syndicate`):** 5 or more distinct non-null `session_refs` ($N_{\text{sessions}} \ge 5$).
- **Unknown (`unknown`):** Assigned when telemetry lacks authenticated session metadata (e.g., purely anonymous requests where $N_{\text{sessions}} = 0$) or when telemetry is incomplete/truncated.

> [!NOTE]
> The number of distinct actor references ($N_{\text{actors}}$) is tracked and reported separately in cluster metadata (`actor_count`), but it **does not alter the session-based size label**. Under the bridging guard in §3.4, distinct actors are partitioned into separate clusters (unless bound by an anomalous shared session with `identity_conflict`), so $N_{\text{actors}} \le 1$ under normal operation. Weak links never alter cluster size.

### 3.6 Attribution Limits & Telemetry Constraints
> [!WARNING]
> Contract telemetry currently lacks client IP addresses, user-agent strings, TLS fingerprints, and network flow metadata.
> Multi-session clustering is strictly a **heuristic inference** based on target overlap and temporal proximity. It does not provide forensic proof of common adversary control. Sequential ID traversal alone never proves malicious coordination. Blue must never fabricate identity linkages where data is missing.
> 
> **Actor-Session Rotation Heuristic:** Observing an authenticated actor rotate to a fresh session after containment of an earlier session is tracked strictly as an informational heuristic note on the cluster (`notes: ["actor_session_rotation"]`). Because multi-session attribution is heuristic and session tokens can be cycled, actor rotation does not alter risk scoring components and never awards persistence credit. All persistence credit is strictly session-level per §4.1.4.

## 4. Explainable Additive Risk Scoring Model

### 4.1 Concrete Additive Scoring Formula (Codex Model)
Per Decision 0006, Blue adopts an explainable, deterministic additive risk scoring formula bounded between 0 and 100:

$$\text{RiskScore} = \min\Big(100, \text{Impact} + \text{Exposure} + \text{Breadth} + \text{Persistence}\Big)$$

*(Note: The outer $\min(100, \dots)$ clamp is mathematically redundant because the maximum sum of the bounded components is 100 by construction per §4.1.5; it is retained in the formula purely as a defensive safeguard so implementers do not read it as a real active clamp.)*

Where each component is defined as:

1. **Impact ($\text{Impact} \in \{10, 40\}$):**
   - **$\text{Impact} = 40$**: Certain, policy-verified violation (HTTP 200 on private record owned by another user or anonymous read). Note: Certainty of violation reflects verified data exposure and is independent of whether an authenticated session exists to contain (see §5.2).
   - **$\text{Impact} = 10$**: Uncertain probing or repeated denied access (HTTP 401/403 attempts on protected routes).
2. **Exposure ($\text{Exposure} = \min(20, 5 \times N_{\text{unauth\_resources}})$):**
   - 5 points per distinct private resource successfully read by an unauthorized actor, capped at 20 points (maximum reach achieved at 4 resources).
3. **Breadth ($\text{Breadth} = \min(15, 5 \times \max(0, N_{\text{sessions}} - 1))$):**
   - 5 points per additional implicated non-null session beyond the first, capped at 15 points (maximum reach achieved at 4 total sessions).
   - **Non-Negative Guard:** If $N_{\text{sessions}} = 0$ (e.g. anonymous read with no session reference), $\max(0, 0 - 1) = 0$, ensuring $\text{Breadth} = 0$ and never negative. Null session references are excluded from $N_{\text{sessions}}$.
4. **Persistence ($\text{Persistence} \in \{0, 25\}$):**
   - **$\text{Persistence} = 25$**: Persistence is a session-level fact awarded when positive evidence shows an unauthorized read completed by the **exact same session reference** (`session_ref`) strictly after that same session's successful applied revocation (`defense.applied` with action `revoke_session`) matching the active target, version, assessment, and data source. Specifically:
     1. **Authoritative Event-ID Ordering:** Per `shared/contracts/README.md`, event IDs on the event stream provide authoritative order, while `event_id` directly on telemetry records is a field proposed for B-12; timestamps are display data only. Persistence strictly requires $\text{event\_id}(R_{\text{unauth}}) > \text{event\_id}(\text{defense.applied})$. The blue design specifies this proposed B-12 contract dependency and assumes core supplies authoritative event IDs on telemetry records in future milestones; in the current contract shape where telemetry records lack `event_id`, persistence ordering cannot be evaluated live and remains inconclusive. Timestamps are display only and never determine ordering. If authoritative event IDs are missing or unorderable on either record, ordering is inconclusive: $\text{Persistence} = 0$ is awarded and cluster notes records `"inconclusive_ordering_missing_event_id"`.
     2. **Same-Session Restriction & No Actor-Rotation Credit:** Persistence applies strictly to the revoked session itself. If an adversary actor rotates to a fresh session after an earlier session was revoked, the fresh session receives $\text{Persistence} = 0$. The rotation is recorded purely as an informational cluster note (`notes: ["actor_session_rotation"]`), reflecting heuristic actor-level inference without score escalation.
     3. **Revocation of Another Session:** An unauthorized read by session $S_1$ after the revocation of a different session $S_2$ never earns persistence credit for $S_1$ ($\text{Persistence} = 0$).
     4. **Cross-Cluster Session Attribution:** Persistence is credited directly in the cluster that contains the post-revocation unauthorized read, even when the 60-second inactivity window ($W$) or 300-second maximum cluster lifetime cap ($L_{\max}$) has split the campaign into a separate, subsequent cluster. The scoring engine evaluates `previous_defenses` across the entire assessment history for that same revoked session reference.
     5. **Strict Suppression:** Unexecuted proposals (`defense.proposed`), pending defenses, rejected defenses, and failed defenses (`defense.failed`) **never earn persistence credit** ($\text{Persistence} = 0$).
   - **$\text{Persistence} = 0$**: No post-execution exposure observed, exposure occurred prior to containment execution, ordering reference missing, or exposure completed by a different/fresh session.
5. **Maximum Score by Construction:**
   The maximum component sum is $40 + 20 + 15 + 25 = 100$, so the maximum risk score is 100 by construction. No valid combination of bounded components can exceed 100. Consequently, the outer $\min(100, \dots)$ clamp in the formula is mathematically redundant; implementers should note it is included solely as a defensive clamp and does not perform active truncations under valid inputs.

### 4.2 Severity Bands
The resulting integer score maps directly into four operational severity tiers. Band evaluation is a pure scalar mapping function of the composite integer score $\text{RiskScore} \in [0, 100]$:
- **Low (0 – 24):** Probing, low-rate reconnaissance, denied authorization attempts. Attainable component examples: $\text{Impact}=10, \text{Exposure}=0, \text{Breadth}=0$ (score 10) or $\text{Impact}=10, \text{Exposure}=0, \text{Breadth}=10$ (3 probing sessions, score 20).
- **Medium (25 – 49):** Broad probing campaigns across multiple sessions ($\text{Impact}=10, \text{Exposure}=0, \text{Breadth}=15$, score 25; 4+ probing sessions), or isolated unauthorized reads with minimal exposure ($\text{Impact}=40, \text{Exposure}=5, \text{Breadth}=0$, score 45).
- **High (50 – 74):** Verified unauthorized exposure across multiple resources or multi-session crew exfiltration. Attainable component examples: single session reading 2 private resources ($\text{Impact}=40, \text{Exposure}=10, \text{Breadth}=0$, score 50), or 3-session crew reading 4 private resources ($\text{Impact}=40, \text{Exposure}=20, \text{Breadth}=10$, score 70).
- **Critical (75 – 100):** Multi-resource unauthorized exfiltration combined with wide session breadth or persistent post-containment bypasses. Attainable component examples: 4+ sessions reading 4+ resources without persistence ($\text{Impact}=40, \text{Exposure}=20, \text{Breadth}=15$, score 75), or multi-resource persistent campaign ($\text{Impact}=40, \text{Exposure}=20, \text{Breadth}=15, \text{Persistence}=25$, score 100).

### 4.3 Standards Alignment & Rejection of CVSS v4
- **Rejection of CVSS v4.0:** CVSS v4.0 is designed to assess static, intrinsic characteristics of software vulnerabilities across disparate systems. It is fundamentally ill-suited for scoring dynamic, real-time behavioral telemetry within an active incident.
- **Adoption of NIST Risk Concepts:** Blue's scoring model aligns conceptually with NIST incident response and risk assessment publications. All weights, scoring factors, and thresholds are proposed project adaptations, not standards-mandated values.
- **Standards Alignment & Verification Status:**

## 5. Confidence-Driven PACE Response Matrix

### 5.1 PACE Tier Hierarchy & Trigger Table
Adapted as a loose operational planning analogy from U.S. Army Communications Planning (FM 6-02 / FM 6-0), Blue organizes response options into a prioritized hierarchy based on confidence and potential disruption to legitimate business operations:

```
  PRIMARY (P)     -->  Tactical Containment (revoke_session)
                       Certain signal required; non-empty session_ref; narrow blast radius
                       
  ALTERNATE (A)   -->  Source Remediation (apply_patch: ownership-fix-001)
                       Proposable on containment bypass or anonymous read; execution draft
                       
  CONTINGENCY (C) -->  Route Hardening (reroute / re-auth)
                       [UNAVAILABLE in M1] Requires B-12 contract extension
                       
  EMERGENCY (E)   -->  Target Lockdown / Reset
                       [HUMAN-GATED NOTICE ONLY; UNAVAILABLE] Autonomous proposal/lockdown prohibited
```

### 5.2 Confidence as an Action Gate
In accordance with Decision 0005, response triggers are strictly partitioned by signal certainty:
1. **Certain Signals (Containment Authorized):**
   - Confirmed HTTP 200 cross-user private read with a valid non-empty `session_ref` (`detection.py:cross_user_read`).
   - **Response:** Immediate proposal of **Primary** containment (`revoke_session`).
   - **Per-Event Owner Protection Rule:** Protection of the resource owner is strictly evaluated per event per §5.4.1: an authenticated session is exempt from containment only for reads of its own resources (legitimate owner access never triggers containment). A session remains fully containable for its own confirmed unauthorized reads of other users' resources, even when that session's owner is concurrently a victim on another resource (see TEST-NEG-03B).
2. **Anonymous Read Exception (Inconclusive for Containment):**
   - Confirmed HTTP 200 anonymous private read (`detection.py:anonymous_read`).
   - While certainty of policy violation is 100% verified ($\text{Impact} = 40$), the absence of an authenticated session identifier ($N_{\text{sessions}} = 0$, cluster size `unknown`) makes the event **inconclusive for Primary tactical containment** (`revoke_session`).
   - **Response:** Primary is skipped; Blue immediately routes to **Alternate** (`apply_patch` proposal) without emitting invalid or placeholder session revocation proposals.
3. **Canary Marker Trigger (Unavailable in M1):**
   - Triggering of an instrumented canary record ("dye pack") is **UNAVAILABLE** under current telemetry (contract lacks canary markers; requested under B-12).
   - When supported, a canary trigger alone DOES NOT authorize revocation without:
     1. Trusted telemetry provenance from core.
     2. Access policy check confirming the read is unauthorized (an authorized owner reading their own record marked with canary metadata is legitimate and must never trigger containment).
     3. A verified, non-empty offending `session_ref`.
4. **Uncertain Signals (Containment Prohibited):**
   - High request volume, rate spikes, or cluster size inferences.
   - Repeated HTTP 403/401 denied attempts (`detect-probing`, producing `attack_type: "denied_probing"`; specified under Group B, not yet built in `detection.py`; closing task **B-09**).
   - Inferred sequential ID traversal without successful private data exposure.
   - **Response:** Logged as evidence, monitored in incident reporting, and accumulated for risk scoring. **Never triggers automated session revocation or user lockout.**

### 5.3 Detailed Tier Definitions

#### Primary (P): Tactical Containment (`revoke_session`)
- **Action Type:** `revoke_session`
- **Parameters:** `{"session_ref": "<offending_session_id>"}`
- **Trigger Rule:** Single certain cross-user read alert on `target_version` with non-empty `session_ref`.
- **Blast Radius:** Narrow. Terminates only the specific, offending session reference.
- **Contract & Implementation Status:** **Partly implemented (Target design)** (Session revocation proposal generation is implemented in `proposals.py:propose_session_revocations`, but the circuit breaker (5 proposals per rolling 60s), deterministic queue ordering, queue-depth reporting, and operator notices/alerts are specified, not built; see §5.5).

#### Alternate (A): Source Remediation (`apply_patch`)
- **Action Type:** `apply_patch`
- **Parameters:** `{"patch_id": "ownership-fix-001", "base_version": "lab-v1"}`
- **Trigger Rule:** Alternate fires when a confirmed unauthorized read on the same protected path and target version has an authoritative event ID strictly after a successful applied revocation (`defense.applied` with action `revoke_session`) on that path ($\text{event\_id}(R_{\text{unauth}}) > \text{event\_id}(\text{defense.applied})$).
  1. **Containment Bypass (Post-Revocation Leak):**
     - The read may come from the **revoked session itself** (which demonstrates containment bypass, earns $\text{Persistence} = 25$ under §4.1.4, and whose duplicate Primary `revoke_session` proposal is suppressed by deduplication under §5.4.4, leaving Alternate as the applicable and required automated response); OR
     - The read may come from a **fresh session** (representing an adversary pivot; while a fresh session by the same actor generates an informational heuristic note `"actor_session_rotation"` for cluster telemetry without score escalation, the Alternate trigger itself does not depend on actor identity).
  2. **Anonymous Unauthorized Access:**
     - A confirmed unauthorized read observed where no session exists to revoke ($N_{\text{sessions}} = 0$, cluster size `unknown`), rendering tactical Primary containment inconclusive. When multiple anonymous clusters on the same route arise in an observation, each maintains separate evidence, but the observation emits exactly one deduplicated `apply_patch` proposal overall for the `(path, target_version)` pair per §5.4.4.
   - **M1 Missing Event-ID Limit for Containment Bypass:** In the current M1 contract shape where telemetry records lack an authoritative `event_id`, blue is stateless and cannot distinguish a replayed pre-revocation record from a new read; containment bypass cannot be detected. Duplicate Primary `revoke_session` proposals are suppressed by deduplication, no automated Alternate `apply_patch` proposal is emitted on the unorderable bypass path, persistence remains 0 ($\text{Persistence} = 0$), and Blue records the limitation note `"ordering_unavailable"`. B-12 closes this gap by adding authoritative event IDs.
  - **Deduplication & Single Proposal Rule:** Exactly one `apply_patch` proposal is made per `(path, target_version)` pair and is permanently deduplicated across observations. It is never re-proposed for the same pair. A new proposal is possible only for a new `target_version` (for example, a patched version that is exposed again). If unauthorized exposure persists after the 30-second remediation dwell measured from patch application (`defense.applied`), Blue produces no second patch proposal; instead, persistence evidence is recorded and Blue escalates to Contingency under trigger (a) of the PACE trigger table (§5.1).
- **Operational Reality:** Pre-packaged source patch applying ownership verification logic to `GET /api/orders/{id}`. Proposable by blue, but the patch artifact `defenses/patches/ownership-fix-001/` remains a **draft** until Member 3 publishes the lab handler. Core executors must refuse live execution of draft patches until promoted under task B-13.
- **Contract & Implementation Status:** **Partly implemented (Target design)** (Patch proposal generation exists in `proposals.py:propose_ownership_patch` with draft manifest, but code currently proposes on any alert alongside revocation deduplicated by `patch_id` only; see §5.5).

#### Contingency (C): Route Hardening / Service Degradation
- **Action Type:** `reroute_endpoint` / `enforce_reauth`
- **Parameters:** `{"route": "/api/orders/{id}", "fallback_target": "/api/secure-orders/{id}"}` *(Illustrative placeholder: exact parameter schema and allowable targets to be defined under task B-12. In accordance with repository security rules, security tools operate only on registered lab targets and reject arbitrary destinations; any fallback route or destination must resolve strictly through the fixed target registry or pre-approved route catalog).*
- **Trigger Rule:** Defined by the settled escalation triggers in the PACE trigger table (§5.1):

### 5.4 Anti-DoS Safeguards & Collateral Damage Prevention
1. **Targeting Rule (Per-Event Protection):** Protection of the resource owner is defined strictly per event, not per person or session. A session is exempt from containment only for reads of its own resources (an owner accessing their own data legitimately never triggers containment). A session remains fully containable for any confirmed unauthorized read of another user's private resource, even when that session's owner is also a victim of another session in a concurrent or subsequent event. Containment targets strictly the `session_ref` observed completing an unauthorized action; a session is never targeted for revocation because its owned resources were accessed by an attacker.
2. **Lockout-as-a-Service Prevention:** Denied attempts (HTTP 401/403) never trigger account locking, IP blocking, or revocation.
3. **Circuit Breaker & Syndicate Containment Queueing:**
   The circuit breaker must not be a switch an attacker can flip to disable defenses. An actor who opens many sessions must never suspend containment of sessions that completed a confirmed unauthorized read.
   - **Specified and OFF by Default:**
      The 5-per-60-seconds cap, the queue, the depth fields (`containment_queue_depth`, `oldest_wait_seconds`), and the operator notices/alerts are **specified but OFF by default**, because current code (`proposals.py:propose_session_revocations`) emits one proposal per offending session with no cap. They may be enabled **only after core confirms two B-12 dependencies**: (1) core retains and replays unproposed offending telemetry across sliding windows, and (2) core supplies valid core-stamped event timestamps on defense events in `previous_defenses`. Until both dependencies are confirmed in place, **no deferral occurs**: all confirmed offending sessions in an observation are proposed in that observation, exactly matching today's uncapped code behavior. The guarantee that confirmed revocations are "never dropped or permanently suppressed" holds **only when the cap is enabled with those B-12 dependencies in place**; enabling the cap earlier without core telemetry retention could silently lose deferred sessions when the telemetry window rolls over. Because Blue is stateless, if core omits deferred offending telemetry Blue has neither those sessions nor a pending-queue reference and cannot detect the loss or autonomously propose their revocations; this is why the cap stays OFF by default until core confirms retention and valid timestamps (the enablement prerequisite), and why there is no automatic fallback for lost retention. Detection of retention failure and recovery must be handled by core using persisted pending state or an explicit capability/health signal.
   - **Where Queue and Rate-Limit State Lives Across `observe()`:**
     The blue entry point `observe()` is functional and derives all queue and rate-limiting state deterministically from its input context: `previous_defenses` plus current alerts from `telemetry`. Already proposed or contained sessions are identified from `previous_defenses` (matching `proposals.py:_revoked_sessions`). The 5-per-60-seconds rolling window counts the core-stamped event timestamps (`timestamp`) of `defense.proposed` events already in `previous_defenses`. Under `shared/contracts/README.md`, contract v1 events already carry the required field `timestamp` (`event_required`), which provides the core-stamped event timestamp. `observe()` already validates and rejects `previous_defenses` events that lack the required contract keys, so a malformed event cannot reach the rate-limit logic.
      - **Fail-Safe for Rate Window Computation (Across Observations):** When the rate window cannot be computed for any reason (e.g. invalid timestamp formatting or unparseable event timestamps on previous defense events), Blue falls back to uncapped proposal emission for all confirmed offending sessions in the observation, records the explanatory note `"rate_window_unavailable"`, and immediately raises an urgent human operator alert in `notes` and incident reporting (`rate_window_unavailable: unparseable proposal timestamps in previous_defenses; failing open to uncapped proposals to prevent containment stall; operator alert`).
        - *Trade-off and Rationale:* A fail-closed cap when timestamps cannot be parsed would treat all prior proposals as inside the window; once 5 proposals exist in `previous_defenses`, capacity would drop to 0 indefinitely with no time-based mechanism to release capacity, stalling containment of confirmed unauthorized reads indefinitely. Failing open accepts the operational risk of elevated proposal rate to guarantee that active unauthorized exfiltration is contained without indefinite stall, while alerting human operators immediately to repair telemetry timestamps.
     - **Telemetry `event_id` vs Event `timestamp`:** Note that `event_id` on telemetry records (not the event timestamp on defenses) is the field that does not exist yet under the current contract (closing under B-12).
     - **Core Evidence Retention Contract Requirement (B-12):** To prevent queue loss when core advances its telemetry window or applies sliding batches, core guarantees that telemetry records for confirmed unauthorized reads whose sessions have not yet been emitted as proposals in `defense.proposed` are retained and included in `context['telemetry']` on every successive `observe()` invocation until a proposal is emitted (or core explicitly persists and passes the pending uncontained queue). Thus, `observe()` reliably reconstructs the pending queue by evaluating all unproposed offending sessions present in retained telemetry against `previous_defenses`, even after the original telemetry window rolls over.
   - **Guaranteed Queueing for Confirmed Violations:** When the cap is enabled with B-12 dependencies in place, revocations for sessions with a confirmed unauthorized 2xx read are **never dropped or permanently suppressed**. When multiple offending sessions are detected (such as in a syndicate attack with 5+ sessions), containment proposals are queued in a fixed, deterministic order:
     1. Primary sort: earliest confirmed unauthorized read event ID when present; when `event_id` is absent (the current M1 contract shape), the queue falls back explicitly to ordering by earliest confirmed unauthorized read using `(core timestamp, request_id)` in ascending order, the exact same deterministic fallback as the clustering rule (§3.1.2). This makes pure `observe()` queue tests deterministic on the current contract.
     2. Tie-breaker: `session_ref` in ascending alphanumeric order.
   - **Bounded Emission Batches & Trailing Window Rate Limiting:**
     A maximum of 5 `revoke_session` proposals (counting `defense.proposed` events directly rather than applied revocations, so a proposal whose defense later fails still consumed capacity; this is deliberate to prevent a failing executor from being flooded) are emitted per rolling 60-second observation window across the entire assessment (not per cluster). A queued session is emitted at the first observation where fewer than 5 proposals were emitted in the trailing 60 seconds, in the fixed deterministic order. Nothing is ever dropped.
     - **Rate-Window Boundary Semantics:** The rolling rate window is strictly half-open: $(t - 60\text{s}, t]$. A proposal emitted at $t_{\text{prop}}$ counts against the rate limit at time $t$ if and only if $t - 60\text{s} < t_{\text{prop}} \le t$. Consequently, a proposal exactly 60 seconds old ($t - t_{\text{prop}} = 60\text{s}$) no longer counts, and capacity is released at exactly $t_{\text{prop}} + 60\text{s}$. This differs from the inclusive 60-second clustering window ($t - T_{\text{last}} \le 60\text{s}$) because clustering links contemporaneous activity within an elapsed interval, whereas rate-limiting capacity releases the moment the full 60-second cooldown has elapsed.
     - **Scheduling Rule:** At each observation invocation, blue evaluates recent proposals in `previous_defenses` falling within the trailing window $(t - 60\text{s}, t]$ to determine remaining capacity. Blue emits queued sessions in the fixed deterministic order while fewer than 5 proposals fall in the trailing window. Queued sessions beyond available capacity remain in the pending queue. Nothing is ever dropped.
     - **Real Delay & Absence of Wall-Clock Guarantees:** Because `observe()` is an advisory function invoked externally by core, the real delay experienced by a queued session depends on when core calls `observe()`. The specification makes **no wall-clock guarantee** beyond: *the oldest queued session is emitted first once capacity exists and `observe()` runs*.
     - **Safety Net: Depth Accounting, Circuit Breaker Flag, Operator Notices, and Human Operator Alert:** The queue depth, oldest wait duration, circuit breaker status flag, and operator notices/alerts serve as the operational safety net:
       - Every observation reports `containment_queue_depth` (the pending depth measured strictly after emission, i.e., confirmed offending sessions still waiting for a proposal) and `oldest_wait_seconds` in status and cluster metadata so backlogs are visible while they grow.
       - **Circuit Breaker Status Flag (`circuit_breaker_tripped`):** The flag `circuit_breaker_tripped` is set to `true` whenever the cap deferred at least one confirmed offending session in this observation, meaning pending depth after emission is 1 or more ($D \ge 1$). It is `false` otherwise ($D = 0$).
       - **Operator Notice vs. Human Alert (Separate Fields):** The operator notice ($D \ge 5$) and the human alert ($D \ge 10$) are separate fields from the `circuit_breaker_tripped` flag:
         - **Normal Queue Operation ($D \le 4$):** When pending depth after emission is 4 or less ($1 \le D \le 4$), `circuit_breaker_tripped: true` is set (at $D \ge 1$), but neither operator notice nor operator alert is emitted; proposals are queued and processed in normal deterministic order as capacity permits. When $D = 0$, `circuit_breaker_tripped: false`.
         - **Human Operator Notice when Pending Depth After Emission is 5 or More ($5 \le D < 10$):** When pending depth after emission reaches 5 or more ($5 \le D < 10$), `circuit_breaker_tripped: true` is set, and Blue records an informational human operator notice (not an alert) in `notes` and incident reporting so a human operator sees the queue growing earlier before it reaches the alert threshold:
           `containment_queue_growing: pending depth after emission is 5 or more (<D> waiting); oldest_wait_seconds: <secs>; operator notice`
         - **Urgent Human Operator Alert when Pending Depth After Emission is 10 or More ($D \ge 10$):** When pending depth after emission reaches 10 or more ($D \ge 10$), `circuit_breaker_tripped: true` is set (with `queued_containment_count: D`), and an urgent human operator alert fires in `notes` and incident reporting, including the full pending queue contents:
           `containment_queue_overflow: pending depth after emission is 10 or more (<D> waiting); offending sessions queued: [<session_refs>]; oldest_wait_seconds: <secs>; human intervention requested`.
   - **Sequential Processing:** In subsequent observations, as earlier proposals age past 60s in $(t - 60\text{s}, t]$ and capacity is released, remaining queued session revocations are emitted in batches of up to available capacity in fixed deterministic order until all confirmed offending sessions are proposed.
   - **Scope of Breaker:** The circuit breaker bounds the rate of automated proposals and prevents unbounded blast radius; it never drops confirmed containment and never falls back to broader automated disruptive actions (no automated route shutdowns, IP blocking, or account lockout). Uncertain probing signals are observed only and never consume circuit breaker budget.
4. **Deduplication, Cooldowns & Remediation Dwell Time:**
   - **Permanent Patch Deduplication:** There is exactly one `apply_patch` proposal per `(path, target_version)` pair, deduplicated across observations, and it is **never re-proposed for the same pair**. A new proposal is possible only for a new `target_version` (for example, a patched version that is exposed again). Sessions or patch actions present in `previous_defenses` are not re-proposed. When multiple clusters on the same route and target version (such as distinct anonymous resource clusters) warrant Alternate in the same observation, exactly one deduplicated `apply_patch` proposal is emitted overall for the `(path, target_version)` pair.
   - **Remediation Dwell Measured from Applied Event:** The 30-second dwell time is defined as the **minimum time before Blue escalates from one PACE tier to the next** (from Alternate source remediation to Contingency route hardening). The dwell is active while elapsed time is 30 seconds or less ($t_{\text{eff}}(R) - t_{\text{eff}}(\text{patch\_applied}) \le 30\text{s}$), and expired when elapsed time is strictly more than 30 seconds ($t_{\text{eff}}(R) - t_{\text{eff}}(\text{patch\_applied}) > 30\text{s}$), measured strictly from the `defense.applied` event for the `apply_patch`, **never from the proposal**.
     - If there is no applied event (the proposal is pending, or core returned `defense.failed` for a draft or stale patch), **the dwell does not start and no conclusion about the patch is drawn**. A pending, draft, or rejected patch never counts as a failed patch, so escalation trigger (a) cannot fire in those states. No escalation claim is made while the patch is only proposed, rejected as draft or stale, or pending. A `defense.failed` outcome goes through the normal failed-defense path to the human operator.
     - Persistence evidence during a pending proposal is still recorded and scored under the single persistence predicate (§4.1.4).
   - **Governing Clock:** Remediation dwell is a time-based duration measured using the same core-stamped, monotonic-clamped timestamps ($t_{\text{eff}}$) used for temporal windows. It is **never used for ordering**; all state and ordering transitions use event IDs per §3.1.
   - **Dwell Behavior & Evidence Retention ($t_{\text{eff}}(R) - t_{\text{eff}}(\text{patch\_applied}) \le 30\text{s}$):** During the 30-second dwell period while elapsed time is 30 seconds or less following patch application:
     - No second `apply_patch` proposal is emitted (prevented by permanent deduplication).
     - PACE tier escalation to Contingency is held in abeyance to allow referee time to retest.
     - Any unauthorized reads observed on the route during the dwell period continue to be scored strictly under the standard risk formula (§4.1): if an unauthorized read satisfies the persistence predicate under §4.1.4 (a post-revocation read by the exact same revoked session reference with authoritative event ID order), it receives $\text{Persistence} = 25$; otherwise (such as an unrevoked fresh session, an unrevoked probed session, or an anonymous read during dwell), it receives $\text{Persistence} = 0$. All telemetry is logged and accumulated in incident evidence dossiers without data loss.
   - **Post-Dwell Expiry Behavior ($t_{\text{eff}}(R) - t_{\text{eff}}(\text{patch\_applied}) > 30\text{s}$):**
     - When elapsed time is strictly more than 30 seconds following patch application, the dwell has expired. If unauthorized reads continue on the remediated route after dwell expiry, Blue produces **zero second `apply_patch` proposals** (permanent deduplication).
     - Persistence evidence seen after the single proposal is recorded and drives reporting; it does not create a second proposal.
     - Because the dwell has expired following patch application and unauthorized reads continue, Blue escalates from Alternate to Contingency under trigger (a) of the PACE trigger table (§5.1), which produces a human notice in `notes` and incident reporting and degrades gracefully in M1 without invalid contract actions.
5. **Reversibility:** Every containment action is transient; every patch action operates on disposable git worktrees/containers supporting instant rollback (`B-08`).

## 6. MITRE D3FEND Armor Model & Bank Heist Presentation

### 6.1 Tactical Alignment
Defensive capabilities are organized under the seven tactics of the **MITRE D3FEND** matrix, providing a conceptual framework for defensive countermeasure engineering. The tactical categories align with formal countermeasure definitions:

| MITRE D3FEND Tactic | Bank Heist Thematic Name (UI Layer) | Technical Defensive Countermeasure |
| :--- | :--- | :--- |
| **Model** | **Blueprint** | Threat modeling, API asset discovery, access-policy definition |
| **Harden** | **Vault Door** | Source-code ownership checks, strict route parameter validation, credential hardening |
| **Detect** | **Watchtower** | Telemetry signature detection, swarm graph clustering, denied-probe alerts |
| **Isolate** | **Security Gate** | Execution environment isolation, network segmentation, blast-radius limits |
| **Deceive** | **Dye Pack** | Decoy canary order records, honey-tokens, randomized record IDs |
| **Evict** | **Ejector** | Narrow session revocation (automated); credential invalidation or account termination are strictly human-gated and out-of-scope for automated blue defense per §5.4 |

> [!NOTE]
> This specification does not use tactic codes; all internal interfaces and data structures reference D3FEND tactics strictly by their canonical names (**Model**, **Harden**, **Detect**, **Isolate**, **Deceive**, **Evict**, **Restore**). Alphanumeric technique IDs (e.g. `d3f:Identifier`) are not assigned at the tactic tier in this design.

### 6.2 Strict Separation of Presentation Layer
- **Arena UI (Omar - Member 1):** The bank heist names (*Blueprint*, *Vault Door*, *Watchtower*, *Security Gate*, *Dye Pack*, *Ejector*, *Recovery Crew*) exist solely as a visual presentation layer for competition spectators and gamified interfaces.
- **Internal Integrity:** All backend data models, telemetry records, evidence logs, incident reports (`incident.py`), and SHA-256 evidence digests use formal technical identifiers (`D3FEND`, and once verified per §12.1, `ATT&CK`, `CWE`, `OWASP`; unverified identifiers are strictly excluded from reports and UI). Metaphorical labels must never supersede technical taxonomies in core data structures.

### 6.3 Proven-State Credit Scoring Scale
Armor protection is never awarded speculatively. Protection credit strictly follows the verified operational state of defensive countermeasures:

```
  PROPOSED / AVAILABLE   -->   0% Credit  (No defensive effect established)
  ACTIVE CONTAINMENT     -->  15% Credit  (Temporary operational suppression)
  APPLIED PATCH          -->  50% Credit  (Source code modified; unverified)
  REFEREE-VERIFIED FIX   --> 100% Credit  (Independently verified by referee)
  FAILED DEFENSE         -->   0% Credit  (Labeled "CRACKED" in UI)
```

1. **Available / Proposed (0%):** A defense exists in the catalog or has been submitted as a proposal (`defense.proposed`). Earns zero armor credit.
2. **Active Containment (15%):** An offending session was revoked via core execution. Awarded only while the revoked session remains inactive and no post-revocation leakage occurs.
3. **Applied Patch (50%):** A source patch was deployed by core to the lab target. Awaits referee verification.
4. **Referee-Verified Fix (100%):** Full credit requires passing both unauthorized denial and authorized access preservation.
5. **Failed / Breached Defense (0% - "Cracked"):** Evaluated downstream by core platform evaluation. Status transitions to **Cracked** if:
   - A positive unauthorized data exposure (HTTP 200 cross-user or anonymous read) occurs on the protected path for the patched version, where the exposure event has an authoritative event ID strictly greater than the patch application event:
     $$\text{event\_id}(R_{\text{unauth}}) > \text{event\_id}(\text{defense.applied})$$
     Equal or earlier display timestamps do not matter (timestamps are display data only; clock skew or equal timestamps never override event ID sequence). An unauthorized read with $\text{event\_id}(R) \le \text{event\_id}(\text{defense.applied})$, including pre-patch and replayed telemetry, never cracks verified armor. If authoritative event IDs are missing or unorderable, the ordering is inconclusive: armor credit remains unchanged and an inconclusive ordering note is recorded; OR
   - An independent referee retest concludes with a verified failure (`result: "failed"`), or conclusively fails authorized owner access preservation with a definitive deny under confirmed authentication and baseline existence (HTTP 403 Forbidden, or HTTP 404 Not Found where a pre-patch baseline owner 200 was confirmed, per §6.4; failed logins, authentication failures, HTTP 401 Unauthorized, unestablished owner sessions, fixture-missing 404s lacking baseline 200, HTTP 5xx server errors, network transport errors, connection resets, and timeouts remain strictly inconclusive and preserve applied 50% credit per repository rules).
   - **Denied Probing Preservation:** Denied probing attempts (HTTP 401/403 alerts) on a patched target version DO NOT crack the defense; they confirm that the patch is actively rejecting unauthorized access. Verified (100%) or applied (50%) credit is strictly preserved upon denied probing.

### 6.4 Downstream Core Posture Accounting Boundary
To maintain strict red/blue context isolation:
- **Provisional Blue Posture (Inside `observe()`):** Blue calculates only an *internal provisional posture* derived from its own proposals and system defense execution events present in `previous_defenses` (0% proposed, 15% contained, 50% applied patch). Under Decision 0004 and Decision 0003, referee verdicts are explicitly excluded from `observe()` context to prevent leakage of ground truth or evaluation findings.
- **Official Referee-Verified Armor Posture (Downstream Core Boundary):** The calculation of official 100% referee-verified armor credit occurs **outside blue's observation context**, within the core platform reporting and referee evaluation plane.
- **Inputs to Core Posture Accounting:** A retest event can only elevate armor credit to 100% if:
  1. The event matches the active `assessment_id`, `target_id`, `data_source`, and specific `tested_path`.
  2. The `patched_version` matches the deployed patch and base version.
  3. The retest independently validates BOTH:
     - **Unauthorized Denial:** Cross-user and anonymous attempts return HTTP 403/404.
     - **Authorized Preservation:** Legitimate owner access (Alice reading order 101, Bob reading order 204) and control route remain functional (HTTP 200).
- **Conclusive Regression vs. Inconclusive Outcomes:**
  - **Conclusive Regression -> Failed Defense (Cracked, 0%):** A conclusive regression occurs when an independent referee retest confirms unauthorized denial but conclusively proves that the patch broke legitimate owner access. Conclusive regression requires all of:
    1. *The owner's session proven valid by a same-retest control:* For example, the owner's authenticated read of their own order list (or another baseline control route) succeeded (HTTP 200). A failed login, unestablished owner session, or HTTP 401 Unauthorized is strictly inconclusive (per repository rules, failed logins and authentication failures are inconclusive, not confirmed regressions).
    2. *The resource proven to exist by a same-retest control:* For example, the resource is confirmed present by a same-retest control check. An HTTP 404 Not Found without a same-retest control proving the resource exists is treated as a missing or reset fixture and remains inconclusive.
    3. *The owner-access check on the patched route returning a definitive deny:* Under confirmed owner session validity and resource existence, the owner-access check returns a definitive deny: HTTP 403 Forbidden, or HTTP 404 Not Found when the same retest's control proves the resource exists. The patch has broken core business authorization logic; the defense state transitions to **Cracked (0%)**. A top-level retest result of `result: "passed"` must never override a check that has `passed: false` or an actual outcome conflicting with expected behavior: that retest is treated as failed.
  - **Partial or Inconclusive Retests -> Credit Preserved in Applied State (50%):** Everything else is inconclusive and preserves credit (maintaining the applied countermeasure at 50% credit in `awaiting_retest`): HTTP 401, failed login, no session established, missing or reset fixture, HTTP 404 without the same-retest control, HTTP 5xx server errors, network transport errors, connection resets, and timeouts. Inconclusive or omitted checks NEVER mark the defense Cracked and NEVER grant 100% credit. The countermeasure remains in its unverified applied state (`applied`, 50% credit in `awaiting_retest`) flagged for rerun. A bare `retest.completed` event with `result: "passed"` that omits authorized access verification is inconclusive and preserves 50% applied credit without granting 100% verified credit.

### 6.5 Aggregation, Path Scoping & Anti-Stacking Rules
1. **No Duplicate Stacking:** Multiple instances of the same countermeasure class (e.g. three session revocations) do not accumulate additive credit.
2. **Path-Specific Bounding:** Armor scores are evaluated independently per supported remediable attack path $p \in P_{\text{remediable}}$ (e.g., $P_{\text{remediable}} = \{\text{IDOR-Orders}, \text{Anon-Orders}\}$).
3. **Operational Probing Exclusion:** Operational reconnaissance paths such as `Auth-Probe` (measuring denied attempts on protected routes) represent normal monitoring activity rather than unmitigated software flaws. Operational probing paths are tracked under detection readiness metrics and are **excluded from the headline software fortification score** so they do not pin armor credit at 0%.
4. **Headline Armor Metric:** The top-level headline armor score shown in the UI is computed as the **minimum** score across all supported remediable attack paths:
   $$\text{HeadlineArmor} = \min_{p \in P_{\text{remediable}}} \text{ArmorScore}(p)$$

### 6.6 Catalog Discipline & Patch Validation
When human players or autonomous blue operators add defenses in the arena:
- **Catalog-Only Upgrades:** Countermeasures must be selected strictly from a pre-compiled, approved catalog of defense identifiers (e.g. `DEF-DYE-001`, `DEF-PATCH-001`). Arbitrary terminal commands, unverified shell scripts, raw code injections, and unreviewed patch files are rejected at the core API gateway.
- **Draft Patch Rejection:** Core executors strictly refuse execution of patch manifests marked with `status: "draft"` (such as `ownership-fix-001` prior to B-13 promotion).
- **Stale Patch Rejection:** A patch whose manifest specifies a `base_version` that does not match the active `target_version` of the lab target represents a stale or incompatible countermeasure. Core executors reject stale patch applications with an HTTP 409 Conflict.

## 8. Known Technical Limitations of this Draft

### 8.1 Documented Technical Limitations
1. **Draft Ownership Patch:** The patch artifact `defenses/patches/ownership-fix-001/` remains a draft until Member 3 publishes the definitive lab order handler route. Executors must refuse application in live modes until promoted under B-13.
2. **Partial-Retest Weakness in `incident.py`:** The current report generator marks an incident as `resolved` if a retest event contains `result: "passed"`, without asserting that all required sub-checks (unauthorized denial, authorized owner access preservation) passed. Core reporting must resolve this before production deployment.
3. **Heuristic Multi-Session Attribution:** In the absence of network-level client identifiers, multi-session clustering cannot establish cryptographic or physical identity linkage. Adversaries utilizing rotating proxies or uncoordinated scanning may induce false-positive cluster grouping.
4. **Telemetry Volume Overflow:** Context ingestion currently raises `ContextError` when telemetry exceeds 10,000 records (`MAX_TELEMETRY_RECORDS`). Adversaries could attempt a volumetric flood to blind the blue agent. Core must window telemetry into sequential batches.
5. **Circuit Breaker Proposal Rate, Queue Limits & Accepted Residual Risk:** While deterministic queueing ensures confirmed offending sessions are never dropped or ignored, the 5-proposal per rolling 60-second window across the assessment bounds proposal emission to prevent flooding the core executor. Pending depth is measured strictly after each observation emits its batch of up to available capacity; the `circuit_breaker_tripped` flag is set to `true` whenever the cap deferred at least one confirmed offending session ($D \ge 1$), and is `false` otherwise ($D = 0$). If the rate window cannot be computed for any reason (e.g. invalid or unparseable proposal timestamps), Blue falls back to uncapped proposals, records `"rate_window_unavailable"`, and raises the urgent human operator alert; failing open accepts the risk of elevated proposal volume to ensure active unauthorized sessions are not stalled indefinitely when timestamps cannot be parsed. Because `observe()` is called externally by core, real delay depends on when core invokes `observe()`, and the specification makes no wall-clock delay guarantee beyond emitting the oldest queued session first once capacity exists. Containment delay grows with the attacker's session count (for example, 16 offending sessions take until $t = 180\text{s}$ across successive observations); this containment delay is the **accepted residual risk** of the 5-per-60-seconds cap, because the cap protects the core executor from being flooded. To provide early operational visibility as the backlog develops, Blue emits an informational human operator notice (not an alert) when post-emission pending depth reaches 5 or more ($5 \le D < 10$), and escalates to an urgent human operator alert with full queue contents when pending depth reaches 10 or more ($D \ge 10$), while every observation reports `containment_queue_depth` and `oldest_wait_seconds`. This trade-off bounds blast radius and prevents runaway automated disruption while maintaining complete backlog transparency.
6. **Authoritative Event-ID Dependency:** Determining persistence credit, Alternate containment bypass triggering, armor cracking, and dwell suppression depends on core supplying authoritative event IDs on all telemetry records. In the current M1 contract where telemetry lacks an `event_id`, ordering decisions are inconclusive: without event IDs, containment bypass cannot be detected, a revoked session that appears in telemetry gets no persistence credit ($\text{Persistence} = 0$), no Alternate proposal is emitted, and Blue records the limitation note `"ordering_unavailable"`. Armor states do not transition without event IDs. This is a known technical gap that B-12 closes.
7. **Actor-Level Rotation Inference:** Because multi-session attribution is heuristic, observing an authenticated actor rotate to a fresh session after containment of an earlier session is treated as an informational heuristic note only, with no score effect.
8. **Anonymous Breadth Understatement:** Anonymous reads of different resources never link per §3.3.3 (no shared session or actor reference), so each scores as its own distinct cluster. Consequently, an anonymous mass-read enumeration does not rise above the single-cluster score (Exposure 5, Breadth 0, Score 45 / Medium); risk and armor reporting understate its aggregate breadth, while Alternate still fires once per path (emitting exactly one deduplicated `apply_patch` proposal for the route and target version).

### 8.2 Proposed Project Choices vs. External Standards
To prevent misrepresenting design decisions as industry standards:
- **Project Choices:** The scoring constants (Impact 40/10, Exposure 5 up to 20, Breadth 5 up to 15, Persistence 25), the score bands (0–24, 25–49, 50–74, 75–100), the 60-second correlation window, the 300-second maximum cluster lifetime, the 5-revocation circuit breaker batch size and 60-second window per assessment, the 30-second remediation dwell time (which defines the minimum duration measured from patch application (`defense.applied`) before Blue escalates from Alternate source remediation to Contingency route hardening while awaiting referee retest, active while elapsed time is $\le 30\text{s}$ and expired when strictly $> 30\text{s}$, while reads continue to be scored and logged under the single persistence predicate without creating duplicate patch proposals), and the bank heist metaphors are **internal project defaults**, not values derived from NIST, MITRE, or OWASP standards.
- **Conceptual Adaptations:** PACE is adapted from military signal planning as a loose operational hierarchy. D3FEND tactics are used as an ontological taxonomy; their credit values (15%, 50%, 100%) are gamified project mechanics.

### 8.3 Unimplemented Contract Dependencies (B-12)
The following capabilities documented in this design cannot execute under `shared/contracts/v1.json` until Diego implements task B-12:

## 9. Open Choices for the Human

This section records architectural trade-offs where independent proposals differed, documenting the default chosen and the rationale for human review:

### 9.1 Alternate vs. Contingency Boundary
- **Disagreement:** Earlier proposals differed on whether multi-session swarm activity should immediately trigger Alternate patch deployment or wait for proof of containment bypass.
- **Chosen Option:** Alternate fires when a confirmed unauthorized read on the same protected path and target version has an authoritative event ID strictly after a successful applied revocation on that path ($\text{event\_id}(R_{\text{unauth}}) > \text{event\_id}(\text{defense.applied})$). The read may come from the revoked session itself (which also earns persistence, and whose Primary proposal is deduplicated, making Alternate the applicable response) or from a fresh session (where actor rotation remains an informational heuristic note for scoring; the Alternate trigger does not depend on actor identity). Alternate also fires on anonymous unauthorized access where no session exists to revoke; when multiple anonymous clusters on the same route arise, each maintains separate evidence, but the observation emits exactly one deduplicated `apply_patch` proposal overall for the `(path, target_version)` pair per §5.4.4. Exactly one `apply_patch` proposal is made per `(path, target_version)` and is permanently deduplicated across observations; it is never re-proposed for the same pair. A new proposal is possible only for a new `target_version`. If unauthorized exposure persists past the 30-second dwell measured from patch application (`defense.applied`), Blue escalates from Alternate to Contingency under trigger (a) of the PACE trigger table (§5.1). Contingency is reserved for persistent exposure under either of the two settled independent triggers in §5.1: (a) confirmed unauthorized read after patch application once dwell has expired ($> 30\text{s}$), or (b) active syndicate ($N_{\text{sessions}} \ge 5$) while patch is pending, draft, stale, or unavailable. A pending, draft, or rejected patch never counts as a failed patch, so trigger (a) cannot fire in those states; trigger (b) can. In M1 where Contingency is unavailable and telemetry lacks authoritative event IDs, containment bypass cannot be detected: only the bypass-triggered Alternate is inert in M1 (no automated patch proposal is emitted on containment bypass, no persistence credit is awarded, and Blue records the limitation note `"ordering_unavailable"`, closing under B-12). In contrast, the anonymous-read Alternate proposal works today as a draft `apply_patch` proposal that core must refuse.
- **Rationale:** Preserves narrow containment as the first line of defense, avoiding unnecessary code modification on initial probes while ensuring immediate remediation when containment cannot apply.

### 9.2 Additive Scoring Constants & Severity Thresholds
- **Disagreement:** Codex proposed bounded formula with 0–24, 25–49, 50–74, 75–100 bands. Antigravity proposed base threat formula with 0–29, 30–59, 60–84, 85+ bands.
- **Chosen Option:** Codex additive model: $\text{Risk} = \min(100, \text{Impact} + \text{Exposure} + \text{Breadth} + \text{Persistence})$, where the outer $\min(100, \dots)$ clamp is mathematically redundant because the maximum component sum is 100 by construction per §4.1.5.
- **Rationale:** Adopted per Decision 0006 consensus; provides concrete, bounded, easily testable components and avoids non-linear scaling.

### 9.3 Cluster Lifetime Cap Value
- **Disagreement:** Codex proposed a maximum cluster lifetime cap ($L_{\max} = 300\text{s}$) to prevent infinite chaining; initial Antigravity proposal used rolling window only.
- **Chosen Option:** Adopted $L_{\max} = 300\text{s}$.
- **Rationale:** Enforces deterministic cluster closure, bounds memory consumption, and prevents long-running low-and-slow campaigns from swallowing all events into a monolithic cluster.

### 9.4 Specialist Role Granularity
- **Disagreement:** Codex proposed framing roles strictly by Monitor and Defender groupings. Antigravity proposed decomposing them into 8 discrete specialists.
- **Chosen Option:** 8 discrete specialist modules implemented once, composed into 2 characters for MVP demo, and unbundled for post-demo swarm.
- **Rationale:** Maximizes unit testability; each specialist module has a single responsibility and zero code duplication between demo and swarm modes.
