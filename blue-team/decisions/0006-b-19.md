## Outcome

Codex and antigravity independently propose the same deliverable. It is a design-only swarm spec at backend/app/agents/blue/design/swarm-spec.md, with no code, dependency, or shared-contract changes. It implements decisions 0004 and 0005. It covers cluster rules, scoring weights, confidence-driven PACE triggers, a D3FEND armor scale with heist names, Monitor/Defender grouping, and a post-demo swarm mode. Both recommend antigravity to draft it, with Claude reviewing isolation and Codex reviewing testability. They differ on details: the risk weights and bands, whether to add a README edit, how many roles there are, and how much to cite external standards. Weights, windows, and names are proposed project defaults, not standards-derived values. Full swarm mode stays gated on B-20 (Joseph's rules check) and a successful first demo.

Shared by both proposals:
- Core stays the only executor (decision 0004). Blue proposes through the existing observe(context, tools) contract, and the referee verifies independently.
- Clustering uses a 60-second window over shared session/actor references and resource overlap. Size labels are solo = 1 session, crew = 2-4, syndicate = 5+.
- Risk scoring is additive and explainable. Bands are published with their components.
- PACE by confidence: Primary contains the offending session on certain signals (unauthorized read, canary hit) and only observes uncertain probes. Alternate is an ownership patch via apply_patch. Contingency is route hardening and needs a contract extension (B-12). Emergency is human-gated.
- The armor scale maps D3FEND's Model, Harden, Detect, Isolate, Deceive, Evict, and Restore to bank-heist names. Credit is state-based: proposed = 0, contained = 15, applied patch = 50, referee-verified = 100, failed = cracked.
- Monitor groups sentry, detector, correlator, and risk scoring. Defender groups PACE planning, remediation, and evidence/posture. Each role is built and tested once, and swarm mode only regroups them with identical policies.
- The spec ends with build tasks and handoffs for Diego (B-12) and Omar (B-14), and the heist names stay a presentation layer.

Details where they differ:
- Codex gives concrete numbers. Risk = min(100, impact 40/10 + exposure 5 per resource capped at 20 + breadth 5 per extra session capped at 15 + persistence 25). Bands are 0-24, 25-49, 50-74, and 75-100.
- Codex also adds a maximum cluster lifetime, a decision-to-section traceability table, and an overall armor headline equal to the minimum score across supported paths.
- Antigravity proposes Base + exposed records x 10 + spread 15/30 + persistence 25. Its bands are 0-29, 30-59, 60-84, and 85+, and it cites NIST SP 800-30 and 800-61.
- Antigravity uses 8 roles (Sentry, Detector, Correlator, Risk Assessor, PACE Planner, Remediation Engineer, Evidence Clerk, Posture Accountant). It also maps attacks to CWE, ATT&CK, and OWASP identifiers and adds a README edit. Codex frames roles by the two groupings only.
- I lean toward Codex's version for the scoring formula and the lifetime cap, because they are concrete and testable. Antigravity's role split and standards mapping are useful as long as the standards are verified. That is my reading only, not a vote.

**Security handling:** Concerns raised by both proposals, and how the approach handles them:
- Red/blue isolation: detection uses only sanitized telemetry and access policy. Red plans, findings, evaluator ground truth, and referee verdicts stay out of blue's context. Armor accounting runs downstream of detection.
- Credentials: they are excluded from telemetry, reports, and digests.
- Lockout-as-DoS and collateral damage: contain only the implicated session, never the resource owner. Denied 403 probes never trigger revocation or lockout. Circuit breakers, cooldowns, and blast-radius limits are required.
- Over-attribution: current telemetry has no client IP or fingerprint, so coordination and swarm size are heuristic. Sequential IDs alone never prove coordination. Anonymous or incomplete size is labeled unknown. Client correlation and canary telemetry need coordinated additions.
- Confidence versus authority: volume, scores, model recommendations, or armor never authorize disruptive action. Certainty comes only from trusted, policy-scoped telemetry. Core enforces permissions and budgets.
- Premature credit: proposed or available controls earn 0. Credit applies only to the tested path and target version, with no stacking of duplicates. Full credit needs referee verification plus unauthorized denial and authorized-access checks.
- Inconclusive outcomes: timeouts, failed logins, missing evidence, and telemetry overflow stay inconclusive and are never reported as successful defenses.
- Catalog and patch discipline: the spec rejects raw commands, arbitrary destinations, and external redirects. It also rejects uncatalogued defenses and draft or stale patches. Game-added defenses must come from a pre-approved ID catalog.
- Contract limits: the contract supports only revoke_session and apply_patch today. Contingency and Emergency are marked unavailable until Diego extends the contracts, and blue must degrade gracefully on the current contract. Emergency always needs a human, with no automatic lockdown or reset.
- Rules gate: Joseph must confirm organizer rules (B-20) before further implementation. The spec must not commit the team to unapproved pre-built assets.
- Known weak points to state in the spec: the ownership patch is still a draft, live integration is incomplete, and the incident report has a documented partial-retest resolution weakness.
- One disagreement to flag: earlier thread proposals differ on Alternate and Contingency. The spec must pick a safe interpretation and list the unresolved choices. Antigravity also lists a README edit, but blue-team rules restrict model writes to blue paths, so that edit should be confirmed in scope.
**Test plan:** Design-only task, so there are no new runtime tests. Both proposals say the same checks apply when the spec is reviewed:
- Review the spec itself: a decision-to-section checklist, completeness of every required element, hand-calculated scoring and cluster examples, and verification of standards mappings against primary sources.
- Review by the other two models: Claude for isolation, fail-safes, anti-DoS, and safe degradation, and Codex for testability and determinism.
- The spec must define future acceptance cases.
  - Positive: a certain cross-user read triggers single-session containment even at low volume; a verified patch earns 100.
  - Negative: owner reads and protected-route denials never trigger containment; repeated 403 probes produce observation only; the victim owner is never revoked; high-volume uncertain probes never become certain through scoring; anonymous exposure produces no fabricated revocation.
  - Boundaries: score caps and band edges, the 60-second window, the maximum cluster lifetime, weak-link bridging, replay deduplication, malformed records before valid duplicates, shuffled input, null identities, and isolation across assessment, version, and source.
  - Failure and limits: flood, overflow, cancellation, and budget exhaustion; stale or draft patches; unavailable actions; and mandatory human approval for Emergency.
  - Armor: reject credit for proposed controls, duplicate stacking, wrong-version retests, partial retest success, and failed authorized-access checks. Monitor/Defender and swarm groupings must give identical decisions and scores for identical evidence.
- Regression commands at implementation review: `cd backend && python -m unittest discover -s tests/blue` (antigravity cites 105 passing tests), `python -m unittest discover -s blue-team/tests` from the repo root, `python scripts/check_handoff.py --self-test`, and `git diff --check`. These show existing regression safety, not live swarm capability. No tests were run in either proposal.
**Rejected alternatives:** - Implementing code or contract changes now. Both proposals reject it: blue should wait for B-20 and for Diego's B-12 contract work, and shipping the spec first avoids code churn.
- Starting with full swarm mode. The spec targets the two-character Monitor/Defender demo first. Swarm mode is the same roles regrouped, and it stays gated on a successful demo.
- CVSS v4 for risk scoring. Antigravity rejects it and uses an explainable additive model citing NIST SP 800-30 and 800-61. Codex also uses a custom additive formula and labels it a project adaptation.
- Treating traffic volume, sequential IDs, scores, or model output as proof of coordination or as authority for action. Both reject this.
- Lockouts or account-level responses that could hit legitimate users or resource owners. Both reject them in favor of narrow session containment.
- Automatic lockdown or reset for Emergency. It is human-gated only.
- Counting proposed or available controls as armor credit. Both reject this.
- Bank-heist names in internal data. Antigravity keeps technical identifiers (D3FEND, ATT&CK, CWE) internally and uses the names only in the UI. Codex's fixed heist-name mapping is consistent with this.
- Open points for the human: which risk weights and bands to adopt, 8 roles versus the grouped roles, whether the README is in scope, and how to resolve the Alternate and Contingency differences.
