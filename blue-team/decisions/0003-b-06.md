## Outcome

All three proposals (claude, codex, antigravity) agree on the core design. Add backend/app/agents/blue/observe.py with an async observe(context, tools) entry point, export it from __init__.py, and have it chain the existing blue modules in order: detect_suspicious_access, propose_session_revocations, propose_ownership_patch (ownership-fix-001, still draft) and build_incident_report. It returns JSON-ready alerts, defense proposals, evidence refs, a short factual summary and the report. It adds no new detection logic, makes no network calls and needs no new dependencies. All three recommend claude as implementer. The proposals differ on three points. (1) Whether the report inside observe may ever reach status 'resolved'. claude says never: no referee or retest events go in. codex wants scoped referee results allowed in and incident.py tightened so that only a complete passing retest resolves. (2) Whether unknown context keys raise or are skipped. (3) Whether incident.py is changed in this task.

Shared core (all three): (1) Validate the context argument and take from it target_id, target_version, data_source, telemetry, access policy, previous_defenses and budgets. (2) Run the existing detector on telemetry against the access policy. (3) Propose session revocations, labeled containment, with previous_defenses used to avoid duplicates. (4) Propose the ownership patch from the fixed patch registry, kept labeled draft. (5) Build the incident report with a generated_at value that is injected, not read from the clock, so output is deterministic. (6) Return a dict with alerts, defense_proposals, evidence_refs, summary and report. Tools stay inert in M1: observations come from core, not from blue calling out. Most of the detail is in claude's proposal: a frozen BlueContext and parse_context(); in-scope vs off-target telemetry split, with off-target records sent to 'skipped'; PatchManifestError caught and recorded as a note, so alerts and revocations still return; output schema tag 'range.blue.observe/v1' with skipped and notes fields; a pre-return check that payloads carry v1 alert.created and defense.proposed required keys; README updated. codex adds: keep IDs stable across repeated observations, and change incident.py's status handling if needed, with matching test_blue_incident.py tests. antigravity adds: build the report only when alerts are present (claude also returns report None when there are no alerts), and accept both telemetry request IDs and existing evidence refs. Why the approach has support: it is about 120 lines of glue that reuses tested modules. Its output reuses existing event_data payloads, so core can emit events without mapping. B-07 can call observe directly instead of reimplementing the order of steps.

**Security handling:** Concerns raised and how the approach handles them. (a) Red/blue separation and ground-truth isolation (all three): context is untrusted, and red plans, candidates, findings, ground truth and verdicts must never reach blue. claude proposes a strict top-level allowlist that raises ContextError on any other key, such as events, candidates, ground_truth or red_*, and never forwards the raw context to helpers. codex agrees on rejecting such data but expects core to supply a bounded context, and does not say whether to raise or drop. antigravity says such data must never be ingested and does not specify a mechanism. (b) Blue must not verify its own fix (all three). claude: build_incident_report receives only blue's own alert/proposal events plus defense.applied and defense.failed outcomes, so status can never be 'resolved'. It can still be 'fix_failed' if an alert appears on a patched version, which is a system observation, not a verification. codex: admit separately scoped system and referee results, and tighten incident.py. Confirmed by reading the code: incident.py _status() currently returns 'resolved' on any last retest result 'passed' without checking that the required checks passed. antigravity: patch proposals stay labeled unverified remediation and revocations stay labeled containment, never a fix. (c) Target, version and assessment scoping (claude, codex): records from another target, version or assessment are skipped, never alerted on, so a version mix-up cannot cause a false alert or hide a post-patch one. (d) Credentials (all three): proposals carry only session_ref and patch_id/base_version. codex: project telemetry and report events onto allowed fields before reporting or hashing. claude: never copy token, cookie, authorization, password, api_key or secret fields, and rely on incident._sanitize before hashing. (e) Policy (claude): fail closed on a missing or malformed access_policy, with no silent fallback to PRIVATE_ORDERS_POLICY. (f) Patch source (claude, codex, antigravity): constant patch ID from the fixed registry, no path from the context, and a draft or stale patch never becomes executable or verified. B-07 and B-08 must test that the executor refuses it. (g) Budgets and cancellation (claude, antigravity): an exhausted budget or a cancellation returns an empty, labeled result with no state change, and this is enforced outside the model. (h) Labels (claude, codex): data_source must be fixture, live or recorded and passes through unchanged. The report labels its provenance and scope so a blue-side report is not mistaken for the final incident record. (i) Partial results (claude): build everything, then return once. The summary carries counts and IDs only. (j) UI exposure (claude): actor_ref and owner refs are references, not secrets, but core should confirm they are fit for display. Open contract item (all three): the exact context key names, the access_policy shape and the tools interface are not defined in shared/contracts. Member 2 must confirm them, and a strict allowlist will reject real contexts until the names match.
**Test plan:** New unittest file under backend/tests/blue/. claude and codex name it test_blue_observe.py; antigravity names it test_observe.py. Tests call observe through asyncio.run with a fake tools object that fails if execution is attempted (codex). Positive (all three): shared fixture telemetry gives a cross_user_read alert, a revoke_session proposal labeled containment, and an apply_patch proposal labeled remediation with patch_status draft. data_source stays 'fixture' and report status is 'open'; the report includes SHA-256 evidence digests (antigravity). codex adds an anonymous successful read case. Output satisfies v1 required keys (claude). Identical input gives identical output (claude, codex). Negative controls (all three): owner reads give no alerts, no proposals and report None; denied 4xx reads give no alert; malformed or missing telemetry fields are skipped without raising; previous_defenses deduplicate revocations; fresh sessions are handled (codex); an exhausted budget returns an empty result without calling the detector or loader (claude, antigravity). Isolation and integrity (claude, codex): extra context keys (events with finding.candidate or finding.verified, ground_truth, candidates) raise ContextError; a missing or malformed policy gives no alerts and no fallback; telemetry from another target, version or assessment is skipped; secret-bearing fields never appear anywhere in the output; data_source 'liveish' or missing is rejected; an unreadable patch manifest still returns alerts and revocations with a note; draft and stale patches are handled. On report status the proposals differ. claude: a smuggled retest.completed 'passed' never yields 'resolved'. codex: containment is never a fix, a proposed or applied patch awaits retest, only a complete passing retest resolves, and incident tests cover this. Commands: cd backend && python -m unittest discover -s tests/blue -v; python scripts/check_handoff.py --self-test; git diff --check.
**Rejected alternatives:** (1) Silently dropping unknown context keys and recording them in notes, for forward compatibility. claude, who raised this option, did not choose it: a silent drop could hide a core bug that leaks red or evaluation data into blue. codex and antigravity did not take a position, so this is not settled. (2) Letting observe consume referee or retest results so its report can reach 'resolved' (codex's direction). claude did not take this route: the contract does not give blue referee verdicts, and the full report with Recover verdicts stays core- or CLI-side (report.py). codex's underlying concern still stands regardless of which design is chosen: incident._status() marks 'resolved' on any 'passed' retest without checking that all required checks passed. If incident.py is not tightened in B-06, it needs its own task before live reporting. (3) Changing incident.py inside B-06 (codex) instead of keeping the diff to observe.py, __init__.py, README and the new test (claude, antigravity). This is open and the vote decides it. (4) Switching report.py to call observe now: deferred to keep the diff small (claude). (5) Using tools for network access, an HTTP client or an executor in M1: all three rejected; tools stay inert or optional. (6) Adding new detection logic or dependencies: all three rejected in favor of reusing existing modules and the standard library.
